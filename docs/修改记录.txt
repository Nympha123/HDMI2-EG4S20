## 六、顶层"显示 bank 安全回退"（功能隐患修复）

问题：`media_player_control` 复位后 `active_index = 0`，而四 bank 预加载会**跳过缺失槽位**（例如卡里没有 PIC1，只会装载 bank1~bank3）。此时 reader 仍按 `active_index = 0` 去读 **从未写入过的 bank0**，而显示门控只要求"任一 bank 就绪"→ 会显示未初始化的 SDRAM 内容（花屏）。

修复（`top_tf_hdmi_audio.v`）：新增 `ctrl_active_index` / `display_bank` 两个网络
```
first_ready_bank = loader_image_complete[0] ? 0 : [1] ? 1 : [2] ? 2 : 3
display_bank     = loader_image_complete[ctrl_active_index] ? ctrl_active_index : first_ready_bank
```
- `active_index` 对应的 bank 已装载 → 按 `active_index` 读（控制权完全归 `media_player_control`）
- 否则（上电初期 / 目标 bank 未装载）→ 读"第一个已装载完成的 bank"

依据：`media_frame_reader` 在 `frame_start` 处采样 `active_index`（源码 line 181），因此换 bank 只会在帧边界生效，不会帧内撕裂；helper 也复用了同一套 bank 基址公式（0 / IMAGE_WORDS / 2× / 3×，与 loader 一致）。
验证：综合门禁无 ERROR，Setup WNS +110 ps / TNS 0 / 0 端点，Hold +421 ps / 0 端点。

## 八、板测问题定位：数码管恒显 `A` + 黑屏（已修复，待复测）

**现象**：第八讲 bitstream（MD5 `109CCEC4…`）烧录后，数码管持续显示 `A`（= ERR_TIMEOUT），屏幕全黑。

**定位过程**：
- `A` 只可能来自"500 ms 内无任何扇区/字节进展"的看门狗。若扫描一张都没找到会显示 `C`（ERR_NO_IMAGE），所以**扫描是成功的**（`scan_resource_valid != 0` ✓，否则 `use_streamer`=0 且不会走加载超时分支）。
- 于是问题在"加载启动了、但没有任何 bank 完成装载"，同时加载期间 SD 层无活动。

**根因**（`SD/sd_card_bmp.v`）：流读取器的启动脉冲被**已删除模块的握手**锁死：
```verilog
if (load_start_pulse) write_req_reg <= 1'b1;
if (write_req_reg && write_req_ack) begin ... file_start_pulse <= 1'b1; end
```
`frame_read_write` 已在第八讲删除，顶层未连接的 `write_req_ack` 恒为 0 → `file_start_pulse` **永远不触发** → FAT32 流读取器（`fat32_file_streamer`）从不启动 → 加载期间 SD 无扇区活动 → 500 ms 后看门狗命中 → `bmp_error = ERR_TIMEOUT`（数码管 `A`），且没有任何 bank 装载完成 → 显示门控关闭 → 全黑。

**修复**：直接由加载启动脉冲驱动（`file_start_pulse <= load_start_pulse;`），不再经过旧握手。综合门禁通过、无 ERROR。

**重要更正（时序）**：修复前门禁显示 "Setup +110 ps / 0 端点"，这是**假象**——`file_start_pulse` 恒 0 使整条 BMP 解析 + 像素流逻辑被综合当作死代码剪除。修复后真实结果为：
- Setup **WNS -438 ps / TNS -101812 ps / 244 端点**，全部在 `sd_card_clk -> sd_card_clk`；

**处理顺序（刻意的）**：先让功能跑通（只改这一处逻辑，便于归因），再单独处理 `media_frame_loader` 的控制路径时序。当前时序与"前七讲定版"（Setup -2152 ps）属同一量级，而前七讲定版已通过 30 分钟长稳测试，故功能复测的风险可控。

### 十三、2026-10-24 切图过渡重做 + 修掉"进区放两遍过渡"

**板测反馈**：切换图片时是"黑幕从左往右退开、约 0.33 s"，硬边纯黑，观感廉价；
而且每次从目录进一个展区，会自动放两遍这个动画。

**两遍过渡的根因（两个叠加）**
1. `menu_ctrl` 在目录里上下移动时会发 `zone_preview`，`sd_card_bmp` 把它也当成"要装图"，
   于是每按一次 W/S 就在后台装一张；等 Enter（`zone_apply`）又装一遍。
   如果预览那次装载还没装完，目录一关就会先看到"预览装载"的过渡，再看到"Enter 装载"的过渡。
2. `zone_apply` 是 video_clk(25 MHz) 域 1 拍脉冲，直接接进 sd_card_clk(50 MHz) 域的
   `sd_card_bmp`，采样次数不确定，同一请求可能被记两次。

**修法**
- `sd_card_bmp.v`：`if (zone_apply || zone_preview)` -> `if (zone_apply)`，目录里不再后台装图；
- `top_tf_hdmi_audio.v`：`zone_apply` 先转 toggle、跨到 sd 域再取边沿成单拍脉冲
  （`zone_apply_sd`），`zone_preview` 直接接 0；
- 过渡触发改成"索引稳定 15 拍后才算换图"（`idx_stable`），多比特跨域毛刺不会再触发两次。

**过渡动画（新）**
- 不再是黑幕，而是"暗到页面底色 `#EEF5FC` -> 换 buffer -> 亮出新图"，
  11 帧 + 11 帧 ≈ 0.37 s，alpha 5 bit、每帧 3 级；
- 关键前提：`frame_fifo_read` 的读地址是**每帧起点 S_ACK 才锁存**的，
  所以换 buffer 早/晚都不会撕裂，可以"等暗到全底色再换"；
- 实现：显示索引 `disp_show_idx` 比 `disp_buf_idx` 慢半个过渡；
  混合公式 `out = C + ((pix - C) * a) >> 5`（带饱和），全亮时走旁路不加延迟；
- 代价：3 个 10x6 乘法器（综合成 LUT，未占 DSP）+ 状态机；同时删掉旧幕帘逻辑。

### 十九、2026-10-24 修 v9 的"图标全没了"

板测：烧了 v9 之后主菜单右侧四个图标整个不见了。

根因是 Verilog 的**乘法位宽**：1.5 倍采样写成

```verilog
wire [7:0] ic_sx_r = (icx * 9'd342) >> 9;      // ✗
```

`*` 在表达式里的结果宽度按操作数最大宽度算（这里 max(12,9) = **12 bit**），
`65 * 342 = 22230` 被截成 `1742`，`>>9` 之后只落到 0..7 —— 也就是永远在采样
图标左上角 8x8 的**空白区**，于是"四个图标全没了"（肉眼就是一片干净背景）。

改法：把操作数先显式扩到 18 bit，用 18 bit 的积再取高 9 位：

```verilog
wire [17:0] ic_sx_m = {6'b0, icx}     * 18'd342;
wire [9:0]  ic_sx_r = ic_sx_m[17:9];            // 0..43 ✓
```

用 Python 按两种语义各算一遍（4 个图标 x 66x66 区域里实际点亮的像素数）：
旧写法 **100** 个（几乎全空），新写法 **2680** 个（正常图标）。板上现象与这个数字完全对得上。

### 二十五、2026-10-25 固化到 FLASH 后"一张图都没有（1 / 0）"、且上电先放一段老音乐

**① `1 / 0` = 扫描一张 BMP 都没找到，而且没有重试**
`sd_card_bmp` 只在 `!scan_kicked && bmp_ready` 时发**一次** `scan_start_pulse`（`scan_kicked` 之后一直为 1）。
固化启动时卡的初始化/首次读偶尔会被打断（CF 配置 FLASH 与 SD 常共用 SPI 引脚，配置期总线活动会惊到卡），

修法：扫描结束若 `img_found_count == 0`，每 ~2 s 自动重扫一次（`rescan_cnt >= 99_999_999`，50 MHz）。

**② 上电那段"老音乐"其实是内部测试音**
`audio_left_src` 原来是三选一：WAV / I2S 接收 / 内部测试音。一张 WAV 都没找到时落到
`hdmi_audio_tone_i2s_64fs` 的连续测试音 —— 每次上电都一模一样，听感就像"又在放老曲子"。
现在音频源只认 WAV：`audio_left/right_src = wav_active_vid ? 采样 : 0`，`audio_valid` 恒 1。
副作用：I2S 接收 + 测试音那套逻辑被综合裁掉，REG -364、DSP -3。

**③ 顺手回退 v15 的"音乐不等首图"**
v15 让 BGM 在 0.5 s 就开始查名并持续播，结果**播放器把 SD 总线占住**（WAV 在仲裁里优先于图片），

### 二十六、2026-10-25 固化启动后 SD 完全没应答（1 / 0 且无音乐）

   并清 `scan_kicked` / `rescan_cnt` / `zscan_started` —— 复位后自动重新初始化和重新扫描；
   每 1.3 s 重试一次，直到卡应答为止。
2. **音频路径跟着一起复位**：`sd_aud_rst_n = sdcard_rst_n & ~sd_retry`，

### 三十、2026-10-25 v21 装载与 WAV 串行化：修掉"音乐一响就装不进图"

**板测两次实验（决定性证据）**
| 实验 | 操作 | 结果 |
|---|---|---|
| 1 | 烧完趁"还没出声"**马上**进各展区 | 黑屏一会 → 出声，各展区声音都对（说明分区装载**能**完成） |
| 2 | 烧完**等音乐放起来**再进展区 | 显示开机那张图，数码管 **5** = 装载 >8 s 没完成 |

两组唯一的差别是：装载的时候 SD 总线上有没有 WAV 的请求。所以卡死不是
FAT/MBR 解析（那会是 4/3），而是**图片装载和 WAV 抢同一条 SD 总线**。

**机制**（`sd_card_bmp` 的仲裁）
- WAV 一侧的请求是**电平**（`fat32_find_file` 在 S_ROOT 一直拉高，
  `wav_stream_player` 在 WS_REQ 等 `!sd_busy`），仲裁里 WAV 优先
  （`arb_req = (wav_sector_req || wav_x_active) ? 1 : img_sd_sec_read`）；
- 反过来，图片的 `sd_sec_read_end` 又被 `(wav_x_active || zscan_active)` 屏蔽；
- 两边同时在场时，WAV 会**吃掉图片那一笔的 done**（它的 `sd_done` 不屏蔽），
  图片这边则被 `wav_x_active` 遮掉 end → `bmp_read` 永远停在 ST_LOAD_DATA →
  `load_busy` 清不掉 → 画面再也不换、A/D 也动不了（都等 `!load_busy`）。

**改法（三处，纯串行化，不动协议）**
1. `sd_card_bmp` 新出 `img_load_active = ~bmp_ready`（图片扫描/装载进行中）；
2. 顶层：装载期间把 WAV 的 `sd_req`（播放器和查找器两条）全部拉低，
   并把播放器看到的 `sd_busy` 抬起来 —— 否则它会在"两个图片扇区之间那 1 拍空闲"
   里溜进 WS_FILL，然后永远等不到自己的 done；
3. `sd_card_bmp` 里 WAV 的 valid/done 改成"只给它自己那一笔事务"
   （`wav_x_active`），别人的 done 不再漏给 WAV。

**代价（要跟用户确认是否接受）**：换区/翻页时图片装载拿满总线，音乐**静音 1~2 s**

### 三十一、2026-10-25 v22 图片优先 + 事务归属仲裁：换区/翻页不再静音

**用户反馈**：v21 修好了（数码管 0，进区能换图），但**翻页（A/D）静音 1~2 s 不可接受**；
换区静音可以接受，更希望直接把"抢总线"这件事解决掉。

**做法：把 v21 的"整段静音"换成两条结构性保证**
1. **图片优先**：`arb_req = zscan ? 1 : (img_req ? 1 : wav_req)`。
   图片只要在请求就给它；WAV 只在"两个图片扇区之间那 1 拍空档"里进来，
   所以装载最多被拖慢几个百分点，绝不可能被饿死（反过来也不会饿死 WAV：
   它每 5 ms 才需要 1 个扇区，而空档每 0.5 ms 就有一次）。
2. **事务归属**：事务开始那一拍锁存 `owner_wav`，`valid/done` 只发给归属方：
   ```verilog
   wav_sector_done  = owner_wav ? arb_done : 1'b0;
   img_sd_sec_end   = (owner_wav || zscan_active) ? 1'b0 : arb_done;
   ```
   v20 卡死的真正机制就是"WAV 把图片那一笔的 done 当自己的，同时图片的 done
   又被 `wav_x_active` 遮掉"——有了 owner，这种双吞在结构上不可能再发生。
3. 播放器看到的 `sd_busy` 改成"总线当前不归我"：
   `wav_sector_busy = arb_busy | img_req | zscan_active`。
   否则它会在图片赢得授权的那一拍（`arb_busy` 还没抬起来）误以为拿到总线，
   溜进 `WS_FILL` 之后永远等不到自己的 done —— 这也是 v20 卡死的另一半原因。
4. `wav_x_active` 整个删掉（不再需要这个"抢锁"寄存器）。

**顺手加的保险**：`load_busy` 挂 8 s 没提交就判定卡死，脉冲 `bmp_read.abort`
把它打回空闲并清 `load_busy`（数码管锁存显示 5）。这样即使偶发卡住，
换区/翻页还能重来，不会整屏永久死掉。`frame_fifo_write` 在新 `write_req`
的 S_ACK 会 `fifo_aclr` 清 FIFO，所以中途放弃一帧不会污染下一帧。

### 三十二、2026-10-25 v23 缩短上电等待：首扫从 A01 扇区开始 + 起播不等首图 + 没图垫底色

**现象**：一切功能正常，但上电要等很久才出图/出声；这期间点进展区是黑屏。

**主因（不是 SD 慢，是扫描起点错）**：`bmp_read` 的开机"找前 4 张 BMP"是
**从扇区 0 一个扇区一个扇区往后扫**。大卡上 FAT32 有两份 FAT，一张 8~16 GB 的卡
FAT 区就有几 MB~几十 MB —— 也就是几千到几万个扇区。每个扇区一次 CMD17 约 0.3~0.5 ms，
**光走过 FAT 区就要几秒到十几秒**，然后才开始读第一张图。这才是"等太久"的根源。

**改法（三处）**
1. **首扫从 A01 的确切扇区开始**：分区扫描器 `fat32_zone_scan` 本来就在开机头几毫秒
   跑了（最高优先级），它已经知道 A01..D10 每个文件的起始扇区。现在
   `scan_start_sector = zone_table_ok ? sec_mem[0] : SCAN_START_SECTOR`
   （扫描范围同理给 start+65535），于是首扫只需读 4 个扇区（A01 命中后按
   `file_sector_count` 跳到 A02/A03/A04）就结束 —— 从"几秒~十几秒"变成**几毫秒**。
   分区表为空（不是 A01..D10 命名）时自动退回老行为，不影响兼容性；
   另加 84 ms 兜底超时（`boot_wait`），即使分区扫描卡住也不会不进扫描。
2. **音乐起播不等首图**：音频 FSM 的门槛从 `display_valid`（要等首图装完）改成
   **`boot_ok` = SD 初始化完成 + 分区扫描完成**（几十毫秒）。v22 的"图片优先 +
   事务归属"仲裁已经保证两者不打架，所以现在 MENU.WAV 几乎上电就响，
   图片随后 ~1 s 出来。
3. **没图时不再黑屏**：图片层加 `img_under = display_valid ? vout_data_adj : C_FADE`
   （页面底色 `#EEF5FC`），并把输出从
   `(display_valid||menu_active||dir_active) ? vout_data_osd : 24'd0` 改成始终输出 OSD 链。
   于是装载期间看到的是"淡蓝页面 + 顶栏时间 + 字幕"，不是纯黑；
   因为只在 `display_valid=0` 时替换，SDRAM 里正在写的半帧不会露出来（不撕裂）。

**上电时间线（预期）**：SD 初始化 ~0.1 s → 分区扫描几毫秒 → **音乐 ~0.1~0.2 s 起** →
首图 1801 个扇区读完 ≈ 0.7~1 s 上屏。原来要 5~15 s。

### 三十四、2026-10-25 v24 固化后开场白被"吃掉"前半段：上电先静音 2.5 s 再起播

### 三十六、2026-10-25 v26 上电时间忽长忽短（真 bug）+ 设置背景要"真的是主界面"

**① 上电时间不一致 —— 是我在 v23 埋的一个竞态**
v23 的 `boot_wait` 从**复位**开始数 84 ms，超时就用"从扇区 0 走 FAT"的慢扫兜底。
但 SD 初始化本身要 100~500 ms —— 等 `sd_init_done` 到来时计时早就溢出了，
于是首扫经常抢在分区扫描（几毫秒）前面启动：
- 抢输 → 用 A01 扇区快扫，上电约 1 s；
- 抢赢 → 退回扇区 0 慢扫（走过几 MB~几十 MB 的 FAT），上电几秒~十几秒。

**改法**：计时改成**从 `sd_init_done` 开始**数，并把窗口放宽到 168 ms
（`boot_wait[23]`，24 bit）。分区扫描只要几毫秒，几乎必定先完成，
上电时间就稳定在"SD 初始化(100~500 ms) + ~1 s 首图"。

**② 主界面点设置，背景不是主界面 —— 根因是字库共用**
`main_menu` 与 `settings_panel` 共用一份 `font_rom`（地址由 `settings_active` 二选一），
所以设置面板一打开就必须 `main_menu.blank(settings_active)` 把菜单整层让开，
否则两边抢字库地址、菜单字模会被带歪。菜单让开之后背景就露出下一层 ——
v25 只是把"图片页"换成"页面底色"，用户要的是**主界面本身**。

**改法**：菜单和面板**各用一份 font_rom**（`u_menu_font` / `u_set_font`），

### 三十九、2026-10-25 v29 分析"滋滋"录音 + 修 WAV 起播/循环的 LBA 差一拍

**录音分析**（`嵌赛\音乐\录音机\录音机-20261025-1716.m4a`，用 Windows Media Foundation
转成 wav 后分析：48 kHz 立体声、9.96 s、峰值 −36 dBFS、RMS −66 dBFS，录得很轻）：

| 频段 | 能量占比 |
|---|---|
| 20~300 Hz | 0.12% |
| **300~1000 Hz** | **89.6%** |
| 1~3 kHz | 9.85% |
| 3~6 kHz | 0.27% |
| 6~12 kHz | 0.05% |
| 12 kHz 以上 | 0.00% |

- 3 kHz 以上几乎没有能量 → 录音里**不存在高频"嘶嘶"**；
- 没有 50 Hz 工频线；
- 按 5.33 ms（缓冲一扇区周期，187.5 Hz）和 21.3 ms 做梳状谱检测，都**没有**比音乐自身
  谐波更突出的"咔哒"梳状线；
- 15~19% 的采样点恰好为 0（说明录得很轻，大部分时间在 16 bit 的最低几位）。

结论：**录音里看不到代码侧"滋滋"的电子痕迹**。要么是显示器/电视喇叭与功放在大音量下的
底噪/失真，要么是录音太轻没录进来。需要用户做两个判别实验（见下）。

**顺手修掉一个真 bug（会产生"咔"的一声）**：`wav_stream_player` 的 `sd_lba` 原来是
"进 WS_FILL 才打一拍"的寄存器，而 `sd_sector_adapter` 是在**请求那一拍**就锁存 LBA 的
—— 所以每次起播/循环重启，实际读的是**上一笔**的 LBA（上电时是 0 = 引导扇区，
循环时是文件最后一个扇区），等于往音频流里插了 512 字节垃圾（≈10.7 ms 的"咔/滋"）。
改法：`assign sd_lba = cur_lba;`（组合输出），锁存的就是当前要读的扇区。

**第二份录音分析**（`录音机-20261025-1729.m4a`，更大声：RMS −48 dBFS、峰值 −16 dBFS）：
- 源文件 `MENU.WAV`：DC≈0、峰值 0.696（−3 dBFS）、能量 100~300 Hz 占 79%、300~1k 18%、6~12k 1.2%；
- 录音在安静段（0.2~0.4 s）各频段是**平的底噪 ≈ −55 dB**（0-50 Hz 略高，有 50 Hz 工频成分，
  那是环境/电源，不是我们发的）；
- 把 3~8 kHz（HF）对 300~1500 Hz（MID）做电平拟合：**HF ∝ MID^0.22**，
  而且 HF−MID 比值随电平升高反而**下降**（低电平 −24.4 dB → 高电平 −29.2 dB）
  —— 这是"**固定底噪**"的特征，不是失真（失真会是 p≈2~3 且比值随电平上升），
  也不是我们 PCM 里的东西（我们的静音样本是精确的 0，DC=0，
  也没有 5.33 ms 周期掉块、没有 512 样本块重复）；
- 结论：**"滋滋"极可能出在 HDMI 接收端之后（显示器喇叭/功放）或者录音设备本身**，
  不在板子送出的数字流里。最终确认只需做上面第 1 条实验。


### 四十、2026-10-25 v30 关音频即完全安静 → 判定为"信号激出来的后级失真"，整体降 6 dB

**用户实验结论（决定性）**：
- 设置里「音量」Enter 关音频（我们输出**精确的 0**）→ **彻底安静**；
- 一放音乐 → **全程"滋滋"**，且随音量成比例。

这组事实把责任锁定在"**被我们的信号激出来的**"那一侧：
后级自噪声（功放底噪）在静音时也应该有，但静音时完全安静 → 不是后级自噪声；
而我们的数字通路是可验证无损的（16 bit → 24 bit 左对齐、DC=0、无掉块/无块重复、
静音样本精确为 0、ACR 的 N/CTS 比例精确）→ 也不是量化噪声。
剩下的最可能解释：**显示器/电视的小喇叭 + 功放在接近满幅时失真/互调**（"滋滋"），
这也完美符合"随音量成比例"和"PC 上放同一文件没有"。

**改法（实验）**：整体数字增益降 6 dB（峰值 −6 dBFS → −12 dBFS），给后级留余量：
```verilog
wire [7:0] audio_gain = (vol_step == 2'd0) ? 8'd13 :
                        (vol_step == 2'd1) ? 8'd32 :
                        (vol_step == 2'd2) ? 8'd64 : 8'd128;   // 原 26/64/128/255
```
验收标准：把电视音量相应开大**到相同响度**后，"滋滋"若明显变小 → 就是后级过载，
可以定在 −12 dBFS 或继续降到 −18 dBFS；若一点没变 → 需要换思路（见下）。

**若降 6 dB 无效，下一步的候选**（按概率）：
1. 显示器对 48 kHz 立体声做了自己的重采样/音效处理 → 试把 L/R 由 "L=R" 改成"只给 L、
   R 给 0"或两边各 −6 dB 的等功率分配，看是否有差别；
2. HDMI 音频包与 ACR 的相位关系异常 → 用 1 kHz 正弦（内部产生）做纯音测试，
   纯音下若有"滋滋"就与音乐无关，能直接分离"数据"和"后级"；
3. 换一台带 HDMI 的显示器/电视对比（用户侧，最省事）。

### 四十四、2026-10-25 v34 修"大图装载被看门狗掐断" + WAV 优先（已固化）

**现象**：A05 要 20 s、A06 近 1 分钟还经常切不出来；快速连按进"曾侯乙"会卡住、音乐也停。

**根因 1：8 秒看门狗是"从装载开始硬算 8 秒"**，而 N 倍图单块读很慢（A05 3.7 MB ≈ 7200 扇区、
A06 8.3 MB ≈ 16200 扇区），8 秒必被 `load_abort` 掐断 ⇒ 页面出不来，`stuck_seen` 还留在数码管码 5 上。
→ 改成 **"8 秒没有任何进展才放弃"**：每收到一个镜像扇区（`sd_sec_read_end`）就把 `load_wdt` 清零。
真挂死仍然 8 s 退出，正常慢读不再误杀。

**根因 2：镜像扇区请求把 WAV 饿死**。`arb_req` 原来是"镜像优先"，而 `bmp_read` 的
`sd_sec_read` 在装载期间几乎一直是高电平 ⇒ 大文件装载时 WAV 拿不到总线 ⇒ 音频断掉/不播。
→ 改成 **WAV 优先**（`arb_req`/`arb_lba`/`wav_grant` 三处对调），并把 `wav_sector_busy`
里的 `img_req` 去掉，让 WAV 随时能插队；镜像装载只被推迟约 7%（WAV 只要 ~100 KB/s）。

**根因 3：装载期间 `sd_sec_read` 常驻有效**，配合"快速连按进分区"容易和 `zscan` 抢总线；
v34 之后 WAV/zscan 都有优先权，镜像读只在空档里推进，不会再互相卡死。

### 四十五、2026-10-25 v35 修行跳过的"行尾窗口"——A05/A06 花屏（已固化）

**现象**：v34 上第 5、6 页画面变成横向拉丝/错行的花屏（OSD 的 `5 / 6` 正常）。

**根因**：`bmp_read` 行跳过时，我在"一行读完"那一拍就把 `row_stop` 更新成**下一条要读的行**的结束偏移，
于是本行末尾到下一行开头之间的字节仍然满足 `bmp_len_cnt < row_stop` ⇒ 被当成像素继续消费
⇒ 每行都会多吞一段字节、像素计数错位 ⇒ 整幅图横向拉丝。

**修法**（同一处）
- 行读完：N>1 时**立刻关窗**（`row_stop <= next_row_off`，即"此刻之后一律丢弃"），
  真正跳到新行那一拍（`len_jump`）再 `skip_until <= next_row_off; row_stop <= next_row_off + row_bytes` 开新窗；
  N=1 时窗口直接接到下一行（顺序读不能断）；
- **最后一行之后彻底关窗**：若 `next_row_off + row_step >= file_len`，`row_stop <= 0`，
  避免文件尾部剩余字节再被写成像素（仿真里 N=2 多写 32 个、N=3 多写 22 个，就是这样来的）。

**验证**：按 v35 的逐字节语义写了 `tools/sim_rowskip.py` 仿真（合成文件 + 真实扇区粒度 + jump），
N=1/2/3 三种情况的像素写入次数**都恰好等于 640×480=307200**（修前 N=2 是 307232、N=3 是 307222）。

### 四十六、2026-10-25 v36 图片按"文件名编号"落位——修第 5/6 页对调（已固化）

**现象**：A05 那张（钟厅）显示"第 5 页"，但底栏 OSD 是 `6 / 6`；A06（钟架尺寸）反过来。图对、页码错。

**根因**：`fat32_zone_scan` 是按**目录里的出现顺序**把图片塞进槽位（`sec_mem[zone*10 + cnt]`），

**修法**：落位改用文件名里的两位数字 —— `dnum_slot = dnum - 1`，A05 永远进槽 4、A06 进槽 5，
与目录顺序无关；`zone_count` 改成"已见最大编号"，并新增每区 10 位的"该槽位有图"位图
（`pm0..pm3`），`rd_valid` 同时检查"编号在范围内"和"该槽确实有图"，这样缺号（比如删了 A03）
也不会读出垃圾扇区。

### 五十三、2026-10-27 v72 任意分辨率缩放（W<=2560 / H<=1920 全支持）+ 白边按页面分级

**1) `bmp_read.v`：任意分辨率（扩展要求 3 从"三档精确匹配"升级到"任意 W x H"）**
- N = max(ceil(W/640), ceil(H/480))，取值 1..4；W/H 用三级比较得到，无除法。
- 按 N 做整数抽取（每 N 个像素取 1 个、每 N 行读 1 行，行跳过沿用 v33 的 jump 机制）。
- **补黑边**：每读完一条源行补 `640-emit_cnt` 个黑像素，文件读完再补 `(480-row_cnt)*640` 个，
  新增 `ST_FLUSH` 状态把一帧凑满 307200 像素（以前少于这个数会等不到写完成 → 看门狗 8 s 超时）。
  补像素每 4 拍发一个，避免冲爆 SDRAM 写 FIFO。
- 约束：W<=2560、H<=1920；N=1 时要求 W==640（更小的图右边黑边没时间在行内补，会串行）。
- 代价：+284 LUT / +19 REG，**0 BRAM**。原有 640x480 / 1280x960 / 1920x1440 三条路径行为不变。

**2) 最左白边：按页面分级补正**

现在 `edge_k` 按页面给：图片页 2、菜单页 4、目录/设置/系统页 0（按要求不补）。
参考值仍取本行 x=16（图片页/菜单页那一列是背景色）。

### 五十四、2026-10-27 v74 修掉"任意分辨率"每行多插一行黑的 bug；白边补像素方案彻底撤销

**上板反馈**：①白边不仅没补上，还出现"上下错位"；②任意分辨率没生效（整屏横向撕裂，A05 5/10 那张也花了）。

**1) 白边：补像素方案彻底撤销**
v73 的"按页面补 2/4 个像素"补出来的是**上一行同列**的内容 —— 人眼对竖直线里的
上下错位极其敏感，所以看起来更糟。结论写进 RTL 注释：输出级回填这条路走不通；
正解是让 OSD 的像素计数按页面提前 D 拍启动（要动 de/OSD 时序，必须单独出包验证）。

**2) 任意分辨率：找到并修掉"每行多插一整行黑"**
v73 里"真像素满 640"和"源行结束"是两个独立条件，各自都会把 row_cnt+1：
1280 宽的图每行最后一个源像素是被抽掉的，于是两个条件各触发一次 —— 每行凭空多写
640 个黑像素，整屏横向撕裂（A05/A06 也一起坏）。
改法：
- 每行只用一个 `pad_left` 记"还差几个黑像素"，补到 0 才 `row_cnt+1`；
- 真像素正好写满 640（N=1 的图）在 emit 那一拍直接结行；
- 源行结束但没写满（out_w<640）才算 `pad_left = 640 - emit_cnt`；
- 新增 `rd_pending`：本行右边黑边没补完之前**不许读下一个扇区**（否则补的像素会
  插到下一行里）；文件读完用 `file_done` 停在"补行"状态，补齐后进 `ST_FLUSH` 补到 480 行。

逐尺寸核对过（每行写出数 = ceil(W/N)，行数 = ceil(H/N)）：
1280x960→640x480、1920x1440→640x480、1280x720→640x360+120、1024x768→512x384+128/96、
800x600→400x300+240/180、1600x1200→534x400+106/80、2560x1440→640x360+120、640x480 原样。

### 五十五、2026-10-27 v75 修"黑边跑到屏幕上方"+ 主界面白边回填

### 五十六、2026-10-27 v76 修 v75 的“点图卡死”（ST_PADTOP 计数器被每拍清零）+ 撤销全部白边回填

**上板现象**：点后面几页概率性卡死（图像不刷新、页码却还在走），后面的图根本看不到。

**根因**：v75 加的 `ST_PADTOP` 里补黑行用的是 `pad_left / row_cnt`，而计数器 always 块的条件还是
`state != ST_LOAD_DATA && state != ST_FLUSH` —— ST_PADTOP 落进了“复位”分支，**每拍把
emit_cnt / pad_left / row_cnt 清 0**，于是 `pad_left` 永远是 0、`row_cnt` 永远到不了 `pad_rows`，
补行永不结束；要等 `sd_card_bmp` 的 8 s 看门狗才 abort，表现就是“点图卡死”。
修法：把 `ST_PADTOP` 加进“正常计数”的条件里（一行）。

v75 只补主界面）都只能在“多补一个像素”和“补的列来自上一行”之间取舍。要根治只能改 de/OSD 时序。

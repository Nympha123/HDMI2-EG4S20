### 3.4 余量与后续建议

- 逻辑余量 **514 片（~257 mslices）**，比 v78（286 片）更宽松，可以再放一个小功能。
- BRAM 只剩 5 块，**不要**再加字库/行缓存/缩略图。
- 若还要腾资源：`u_wav_stream_player` 的 512×16 缓冲仍是 LUTRAM（TD 不吃
  `syn_ramstyle` 属性），可再减半到 256×16（约 −150 mslices），但音频余量会降到 ~2.6 ms。
- 时序瓶颈在 `ext_mem_clk` 的 `frame_fifo_write.state → frame_fifo_read.App_rd_en`
  （6 级逻辑、4 个加法器）。要再抬 Setup，应在 `O_wr_busy/App_wr_busy` 上打一拍，
  属于 SDRAM 仲裁改动，必须单独出验证位。

## 4 现场三个问题的根因与修复

### 4.1 主界面按“返回键(Q)”跳到别的界面

- 根因：`menu_ctrl.v` 在主菜单分支里写了
  `else if (back_ev) menu_active <= 1'b0;` —— 主菜单被直接关掉，露出底下最后一帧图片页，
  用户看到的就是“跳到别的界面”。
- 修复：删掉这条；主菜单上 Q 完全无效。图片页/目录页的 Q 逻辑不变
  （目录→主菜单，图片→主菜单），系统简介/设置页的 Q 仍由各自模块处理。

### 4.2 展区 1 参观完回主界面后，音乐永久静音

根因是**两条音频通路抢同一组 SD 事务**（`sd_card_bmp` 的仲裁只区分“WAV / 图片”，
没区分“WAV 播放器 / WAV 文件名查找器”）：

1. 换曲时 `aud_state` 直接把 `wav_sector_req` 从 `wav_play_req` 切到 `wav_find_req`，
   而播放器此时可能正在 `WS_FILL` 等自己那一笔的 `sd_done`；
2. 查找器把播放器那一笔的 `sd_done` 当自己的、播放器又把查找器那一笔当自己的（互相吞）；
3. 更致命的一种：播放器在 `WS_REQ` 看到 `!sd_busy` 进了 `WS_FILL`，但它的 `sd_req`
   已经被 mux 掉，仲裁再也不会为它开事务 → **永远等不到 done**，而 `ended` 永远不会置 1，
   顶层也不会再给 `restart` → 音乐从此彻底不响，只能断电。

修复（`top_tf_hdmi_audio.v` + `wav_stream_player.v`）：

- 换曲流程改成**串行**：目标变化 → 拉低 `play_enable` → 等 `player_idle`（写侧退回 IDLE）
  → 才 `start` 查找 → 查到后给 `restart` + 新 LBA + `play_enable`；
- 播放器新增 `player_idle` 输出、`WS_FILL` 的 84 ms 事务看门狗（等不到 done 就回 IDLE 重来）；
- `restart` 是 50 MHz 单拍脉冲，直接进 25 MHz 读侧会“看 0/1/2 次”，读指针可能与写指针
  错位 → 现在先拉宽到 16 拍 sd_clk 再打两拍同步到读域；
- 目标曲目号做 1.3 ms 稳定滤波（多 bit 跨时钟域，1→0 时可能扫出 2/3 这种不存在的展区号）；
- 查找器若在流程中间目标又变了，自动放弃重来。

### 4.3 进其他展区仍停在“曾侯乙”那页

两条独立原因，都修了：

1. **SD 读事务可能永久卡死**：`sd_card_cmd.v` 的 `S_READ_WAIT`（等卡回数据令牌 0xFE）
   **没有超时**。卡漏应答（杜邦线/排线接触不良、热插拔、上电抖动）就永久停在该状态，
   `sd_sector_adapter` 的 `busy` 一直是 1 → 图片装载和 WAV 播放都再也拿不到扇区。
   更糟的是此时 `owner_wav` 可能被锁成 1，图片数据被永久屏蔽 —— 表现就是
   “UI 还在动（都是 video_clk 域），图片和音乐全死”。
   - 修复：`S_READ_WAIT` 加 84 ms 看门狗 → `S_ERR`；`sd_card_sec_read_write` 收到
     `cmd_req_error` 立刻撤 `block_read_req`、结束本笔、报 `sd_sec_read_error`；
     `sd_sector_adapter` 的 `sector_error` 以前**恒接 0**（坏扇区被当正常数据拼图），
     现在如实上报；
   - `fat32_find_file` / `fat32_zone_scan` 也各加 84 ms 看门狗（它们卡住会把
     `busy`/`zscan_active` 永久拉高，等于独占 SD 总线）；
   - `sd_card_bmp` 的 `load_abort` 除 8 s 超时外，现在也接受“坏扇区”立刻收笔。
2. **整条 SD 子系统兜底自恢复**（新增，顶层）：总线连续 **336 ms** 没有收尾
   （正常一笔扇区 ≤ 250 µs）就把 SD 核 + 图片装载 + 分区表 + WAV 查找/播放一起复位重来，
   等于自动“重新插一次卡”，不需要断电。

## 6 资源优化：WAV 环形缓冲 1024 → 512

- 现象：把上面这些保护加完后，P&R 一度冲到 **9506 片（97.0%）**，Setup 只剩 +359 ps。
- 定位：`u_wav_stream_player` 的 1024×16 缓冲被 TD 铺成**分布式 RAM（LUTRAM）**，
  占掉约 1000 个 LUT（`syn_ramstyle="block_ram"` 属性 TD 不识别，实测 BRAM 数不变）。
- 处理：`ADDR_WIDTH` 10 → 9（512×16 = 1 KB = 2 个扇区 ≈ 10.7 ms @48 kHz）。
  写侧 `HIGH_WATER = 512-256-8 = 248`，稳态缓冲 ≈5.2 ms；WAV 在仲裁里优先于图片，
  一个扇区 ~250 µs，余量 ~20 倍。
- 结果：8886 片（90.67%），wire length 2.13M → 1.54M，`sd_card_clk` 余量 +414 → +602 ps。

## 9 遗留问题（与 v78 相同，本轮未动）

1. **音频“滋滋”**：已排除 SD/WAV 数据链与显示端（v70t 内部 1 kHz 正弦同样有），
   剩余差异是“官方节拍来自 I2S 12.288 MHz 域、我们来自 25 MHz 小数分频”，

2. **最左 1 px 浅白线**：OSD 比 DE 晚 D 拍（图片页 ≈2、菜单/目录 ≈4），
   三次回填方案都失败，正解是让 OSD 计数提前 D 拍启动，需要单独验证位。
3. **任意分辨率缩放**：RTL 在（`hdr_any_size` 开关，当前 0），上板四次翻车，
   需要先做逐拍 Python 模型再打开。
4. **Setup 余量 +241 ps**：瓶颈在 SDRAM 读写仲裁，非本轮改动引入。
